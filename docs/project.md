# Small LLM Reasoning — Training, Distillation, and Reinforcement Learning

## 1. Problem Statement

Investigate how different LLM training paradigms influence the performance of
small language models. Implement and compare:

- **Supervised Fine-Tuning (SFT)**
- **Knowledge Distillation**
- **Reinforcement Learning (GRPO)**

...to improve mathematical reasoning capabilities, and evaluate the trade-offs
between them across:

- Accuracy
- Training cost
- GPU memory usage
- Inference latency

This is a **controlled comparison**, not just "train a model" — the base
model, dataset, and evaluation harness must stay fixed across all arms so the
comparison between methods is fair.

---

## 2. Core Setup

| Component | Choice | Notes |
|---|---|---|
| Base model | Small model, ~0.5B–3B (e.g. Qwen2.5-0.5B/1.5B-Instruct, SmolLM2-1.7B, Llama-3.2-1B/3B) | Must fit single-GPU training budget with LoRA |
| Task / dataset | GSM8K (primary), optionally MATH subset | Final-answer format makes grading trivial — good for both eval and GRPO reward |
| Teacher model (for distillation) | Larger model, same or compatible family (e.g. Qwen2.5-14B/32B-Instruct, or an API model) | Used only to generate CoT rationales for training questions |

## 3. The Pipeline / Flow

```
                         ┌─────────────────────┐
                         │   Base Model (0)     │
                         └──────────┬───────────┘
                                    │
                    ┌───────────────┼───────────────────┐
                    │               │                   │
              benchmark(0)    [branch A: SFT]      [branch B: Distillation]
              (zero-shot)            │                   │
                                     ▼                   ▼
                          Fine-tune on GSM8K      1. Teacher generates CoT
                          human-written CoT          rationales for the same
                          solutions                   training questions
                                     │               2. Fine-tune a FRESH copy
                                     ▼                  of the base model on
                          ┌─────────────────┐           teacher-generated data
                          │  Model (1): SFT  │           (same recipe as SFT,
                          └────────┬─────────┘           different data source)
                                   │                      │
                             benchmark(1)                 ▼
                                                 ┌──────────────────────┐
                                                 │ Model (2): Distilled │
                                                 └──────────┬───────────┘
                                                            │
                                                      benchmark(2)
                    │
                    ▼
         [branch C: GRPO / RL]
    starts from the BASE model (0) —
    (revised: SFT scored below base,
    so GRPO no longer chains off SFT)
                    │
                    ▼
          ┌──────────────────────┐
          │   Model (3): GRPO    │
          └──────────┬───────────┘
                      │
                benchmark(3)
```

**4 checkpoints to benchmark, identically:**

1. **Base model** — zero-shot, no training. The control.
2. **SFT model** — base model fine-tuned on human-written GSM8K CoT solutions.
3. **Distilled model** — a *fresh copy* of the base model fine-tuned on
   CoT rationales generated by the teacher model for the same questions.
   Mechanically identical to SFT — only the data source differs
   (human labels vs. teacher labels).
4. **GRPO model** — starts from the base model (revised from the original
   plan of starting from the SFT checkpoint, because SFT scored below base)
   and is improved via reinforcement learning with a `<think>...</think>`
   output format, using a correctness reward plus a small format reward.

---

## 4. Why Distillation ≠ "SFT step 2"

Distillation is not a step applied on top of the SFT model — it's a
**parallel branch** starting from the same base model. The only difference
between the SFT arm and the Distillation arm is *where the training labels
came from*:

- SFT: labels = human-written solutions (fixed, external dataset)
- Distillation: labels = teacher-model-generated solutions (fixed, external
  dataset, just generated by an LLM instead of a human)

Both are **off-policy** — see Section 5.

GRPO, by contrast, was originally planned to chain off the SFT model
(RL benefits from a model that already knows the output format). That was
revised: SFT scored below the base model in our diagnostics, so GRPO now
starts from the base model, and the format is taught through the prompt and
the format reward instead. It improves via reward signal rather than
imitation.

---

## 5. On-Policy vs Off-Policy

**Policy** = the model's current behavior/output distribution. It changes
every time the model is updated.

### Off-Policy (SFT, Distillation)
- Training data is **fixed and external** — generated by someone/something
  other than the model being trained (humans for SFT, a teacher LLM for
  distillation).
- Dataset is pre-built once, stored on disk (question + full written
  answer), reused across epochs.
- Learning = imitation (supervised cross-entropy loss) — "copy this correct
  output."
- No reward/advantage needed — just match the target text.
- Cheap: one static dataset, loop over it, mostly backward-pass cost.

### On-Policy (GRPO / RL)
- Training data is **generated live by the model itself**, every training
  step — not pre-written.
- Dataset only needs: question + ground-truth final answer (for grading).
  No reasoning/answer text needed upfront.
- Each step:
  1. Sample a group of completions (e.g. 8–16) from the *current* model for
     a batch of questions.
  2. Grade each completion (reward = 1 if final answer correct, else 0).
  3. Compute **advantage** = reward − group average reward.
  4. Reinforce completions with positive advantage, suppress negative ones.
- Data goes stale fast — once the model updates, old generations no longer
  reflect its current policy, so generation must happen fresh every step.
- Expensive: generation (sampling multiple completions per question)
  dominates training cost, not just the backward pass.

### Core difference (one line)
> Off-policy = learn by imitating someone else's fixed answers.
> On-policy = learn by grading your own answers and reinforcing what
> worked, regenerated fresh every step.

### Advantage (quick definition)
> Advantage = reward − baseline (group mean reward in GRPO). Tells the
> model whether a specific attempt was better (+) or worse (−) than its
> own average — the actual learning signal in on-policy RL.

## 6. Evaluation Harness (shared across all 4 checkpoints)

Build this before training anything, so Model (0)'s baseline numbers exist
for comparison from day one.

- **Accuracy**: exact-match on final numeric answer on held-out GSM8K test
  set (and MATH subset if used). Tools: `lm-evaluation-harness` or a simple
  regex-extract-and-compare script.
- **Training cost**: wall-clock time, GPU-hours, peak VRAM
  (`torch.cuda.max_memory_allocated`), tokens/forward-backward passes
  processed.
- **Inference latency**: tokens/sec and time-to-first-token at a fixed
  batch size/sequence length — ideally via vLLM for realistic serving
  numbers, with and without KV-cache.
- **Memory**: peak inference VRAM at a given batch size.

Keep tokenizer/chat-template identical across all arms — otherwise latency
and accuracy comparisons are contaminated.

## 7. Suggested Order of Work

1. Build the eval harness + get baseline zero-shot accuracy for Model (0).
2. SFT arm (Model 1) — establishes the data loading / LoRA / checkpointing
   pipeline.
3. Distillation arm (Model 2) — reuse SFT pipeline, swap data source to
   teacher-generated rationales.
4. GRPO arm (Model 3) — hardest; starts from Model (1), implement reward
   function, use `trl.GRPOTrainer`.
5. Run the full eval sweep (accuracy / cost / memory / latency) across all
   4 checkpoints and write up the trade-offs.

## 8. Known Pitfalls

- GRPO is sample-inefficient — needs many generations per prompt (group
  size 8–16). Budget compute accordingly.
- Reward hacking: a pure "final-answer-match" reward can let the model
  skip reasoning and still get lucky; consider a small format/length
  reward too.
- Small/empty-variance reward groups (all correct or all wrong) give zero
  learning signal — larger group sizes make useful variance more likely.
- Use LoRA/QLoRA consistently across SFT and distillation to keep compute
  budget comparable across arms.

## 9. Candidate Tooling

- `transformers`, `peft` (LoRA/QLoRA), `trl` (`SFTTrainer`, `GRPOTrainer`)
- `vllm` for fast teacher inference (distillation) and fast generation
  during GRPO rollouts / inference latency benchmarking
- `lm-evaluation-harness` for standardized accuracy evaluation
- Weights & Biases (or similar) for logging training cost / GPU memory
  across all arms in one place
